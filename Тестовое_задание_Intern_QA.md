## Задание 1. «Будильник» — анализ требований и тест-дизайн

### 1. Пробелы и противоречия в требованиях

1. Первое и второе требования противоречат друг другу: первое требование обязывает указать дни недели для создания будильника, а второе позволяет будильник сделать одноразовым, не указывая дни недели

3. Пятое требование чуть-чуть задевает функцию удаления будильника, но нету явно прописанного по этому поводу требования, будет ли реализована данная функция
4. В первом требовании не указаны ограничения значений для минут и часов, аналогично в третьем требовании для “N”(насколько минут отложить будильник)
5. Одноразовый будильник после срабатывания автоматически отключается, это значит что он просто отключится в приложении и у нас будет возможность отложить его при срабатывании или он отключится без повторного срабатывания
6. Одноразовый будильник после срабатывания можно включить и он сработает на следующий день?
7. Что такое зона “долгого сна”, как это должно быть реализовано: это отдельная функция? Что должно произойти после 5 повторения: будильник автоматичсеки выключится или продолжит звонить без возможности отложить
8. После “откладывания” будильника мелодия перестает играть сразу или доигрывает до конца
9. После проигрывания мелодии у будильника без откладывания, мелодия продолжает играть на репите или останавливается
10. Рискованные сценарии с переводом времени на летнее/зимнее(прописано в примере)
11. Как указывается время, выбором из имеющихся значений, что гарантирует не ввести некорректное значение, или вручную на клавиатуре
12. Почему часть требований прописана в **Учтите**, а не в требованиях

### 3. Техники тест-дизайна

Классы эквивалентности. Разделил бы значения времени будильника на валидные (от 00:00 до 23:59) и невалидные (например, 25:00, 12:60, текстовые значения). Проверил бы по одному значению из каждого класса.(Если мы предположим что мы вводим время вручную)

## Задание 2. «Создание заказа» — проверка API и обработки ошибок

### 1. Анализ требований

1. Необходимо уточнить, что `product_id` и  `quantity` это один элемент списка `items`
2. Уточнить какая ошибка возращается, если передали несущетсвующие `user_id` и `product_id`
3. Какой тип данных у каждого поля
4. `product_id` должно отличаться в `items`
5. Приоритет обработки ошибок
6. Что должно происходить при 503: повторный запрос через какое-то время или вывод ошибки пользаку

### 2. Чек-лист тестирования

1. Проверка успешного создания заказа с одним доступным товаров
2. Проверка успешного создания заказа с несколькими доступными товарами
3. Проверка создания заказа без поля user_id
4. Проверка создания заказа без поля items
5. Проверка создания заказа с пустым списком items
6. Проверка создания заказа без поля product_id у товара
7. Проверка создания заказа без поля quantity у товара
8. Проверка создания заказа с quantity = 0
9. Проверка создания заказа с отрицательным или дробным значением quantity
10. Проверка создания заказа с несуществующим product_id
11. Проверка создания заказа с количеством товара, превышающим остаток на складе
12. Проверка создания заказа при недоступном сервисе проверки остатков

### 3. Тест-кейсы API

#### Тест-кейс 1. Успешное создание заказа
**Предусловия:**
- Пользователь с `user_id` = 1 существует
- Товар с `product_id` = 1 существует
- На складе доступно минимум 10 единиц товара
- Сервис проверки остатков работает

**HTTP-метод и endpoint: POST /orders**

**Тело запроса:**

```json
{
  "user_id": 11,
  "items": [
    {
      "product_id": 1,
      "quantity": 10
    }
  ]
}
```

**Ожидаемый HTTP-статус: 201 Created**

**Ожидаемый результат:**
- Заказ успешно создан
- В ответе присутствует идентификатор заказа и статус created
- Заказ сохранён в базе данных
- Данные заказа соответствуют отправленному запросу

#### Тест-кейс 2. Создание заказа с некорректным количеством товара
**Предусловия:**
- Пользователь с `user_id` = 1 существует
- Товар с `product_id` = 1 существует
- Сервис создания заказов доступен

**HTTP-метод и endpoint: POST /orders**

**Тело запроса:**

```json
{
  "user_id": 1,
  "items": [
    {
      "product_id": 1,
      "quantity": -1
    }
  ]
}
```

**Ожидаемый HTTP-статус: 400 Bad Request**

**Ожидаемый результат:**
- Возращается ответ с текстом ошибки
- Заказ не создаётся
- В базе данных отсутствует новый заказ

#### Тест-кейс 3. Создание заказа при недоступности сервиса проверки остатков
**Предусловия:**
- Пользователь с `user_id` = 1 существует
- Товар с `product_id` = 1 существует
- Сервис создания заказов работает
- Сервис проверки остатков временно недоступен (например, его недоступность имитируется с помощью мока)

**HTTP-метод и endpoint: POST /orders**

**Тело запроса:**

```json
{
  "user_id": 1,
  "items": [
    {
      "product_id": 1,
      "quantity": 10
    }
  ]
}
```

**Ожидаемый HTTP-статус: 503 Service Unavailable**

**Ожидаемый результат:**
- Система возвращает ошибку недоступности сервиса
- Успешное создание заказа не подтверждается
- Нет созданного заказа или необоснованного резервирования товара

### 4. Проверка результата

Так как при корректном статусе ответа, может быть например некорректная запись в БД, дополнительно необходимо проверить:

1. Запись в БД и коректность данных, что они соответсвуют тем, которые указали в теле запроса
2. Остатки товара
3. Должен вернуться идентификатор заказа и соответствовать записи в БД

### 5. Бонусный вопрос

Может создаться дубликат заказа, надо задать вопрос: как сервис обрабатывает дубликаты заказов?

### 2.

```sql
SELECT users.name, COALESCE(SUM(orders.total), 0) AS total
FROM users
LEFT JOIN orders ON orders.user_id = users.id AND orders.status = 'completed'
GROUP BY users.id, users.name;
```

### 3.

```sql
FROM users
INNER JOIN orders ON orders.user_id = users.id

```

### 4.

```sql
SELECT users.name, SUM(orders.total) AS total
FROM users
INNER JOIN orders
    ON orders.user_id = users.id
WHERE orders.status = 'completed'
GROUP BY users.id, users.name
ORDER BY total DESC
LIMIT 3;
```

### 5.

```sql
FROM users
```

```sql

INNER JOIN orders ON orders.user_id = users.id
```
